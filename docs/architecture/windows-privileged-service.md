# Минимальная привилегированная Windows-служба

## Назначение

Служба — единственный компонент, которому в будущих этапах разрешено управлять
VPN-драйверами, engine-процессами, маршрутами, DNS и Windows Filtering Platform.
Flutter GUI всегда запускается как обычный интерактивный пользователь.

Этап 8 добавляет настоящий lifecycle Windows Service Control Manager и локальный
named pipe `KenaiVpnControl-v4`. Начиная с этапа 14 служба управляет
WireGuard, AmneziaWG 2.0 и VLESS + REALITY/Xray как независимыми движками.
GUI по-прежнему не получает административных прав. Репозиторий
не устанавливает и не запускает службу автоматически. Dev-скрипты установки и
удаления требуют отдельного elevated PowerShell и явного подтверждения.

## Разрешённый IPC

Текущая версия бинарного контракта допускает только фиксированные операции:

- `Status()`;
- `Connect(profile_handle, protocol, operation_id, kill_switch)`;
- `Disconnect(operation_id)`;
- `CollectDiagnostics()` с обязательной редакцией;
- `Statistics()`;
- импорт строго типизированных профилей WireGuard, AmneziaWG и VLESS;
- `DeleteProfile(profile_handle, operation_id)`.

Подписка на события остаётся будущим расширением контракта и не изображается
реализованной. Статистика Xray в MVP ограничена нулевыми счётчиками без
handshake timestamp; это явно зафиксировано в архитектуре этапа 14.

Запрос не может содержать shell-фрагмент, путь к executable/config, имя службы,
аргументы процесса или firewall rule. Импорт передаёт только поля трёх
типизированных профилей с двойной валидацией; пути, процессы, имена интерфейсов и
системные команды выбираются службой из собственной allowlist-конфигурации.

Named pipe создаётся только локально с явным DACL и запретом удалённых клиентов.
Защищённый DACL запрещает anonymous/network tokens; после соединения служба
получает PID клиента и сверяет его Windows session с активной console session.
Первый экземпляр pipe создаётся с защитным флагом `first_pipe_instance`.
Следующий экземпляр создаётся без этого флага до освобождения текущего.
Начиная с 1.1.8 временная ошибка 231 при создании слушателя обрабатывается
повторной попыткой с уступкой I/O-reactor; ожидание ограничено пятью секундами.
Это позволяет Windows/Tokio закончить операции закрываемого канала. Повторное
использование того же объекта Tokio не применяется: оно сохраняло старую
ошибку чтения после переподключения. После ответа служба ждёт закрытия клиента
не более двух секунд и отключает его. Имя канала остаётся занято службой,
а число экземпляров остаётся ограниченным двумя.
Служба проверяет версию, размер сообщения, enum/range и
уникальность request ID до любого действия. Размер кадра ограничен 32 KiB.

Обрыв или повреждённый запрос одного клиента не завершает цикл приёма следующих
соединений. Если сам слушатель не смог запуститься, служба сообщает SCM состояние
`STOPPED`, а не остаётся видимой как `RUNNING` без pipe. При обновлении установщик
не заменяет бинарник, если действующую службу не удалось остановить: после
резервного копирования настроек нужен обычный перезапуск Windows и повторный
запуск установщика до открытия старого клиента.

Ответ содержит только типизированное состояние и allow-listed код. Текст ошибок
ОС, пути и диагностические подробности через IPC не передаются. `CONNECTED`
возвращается только после запуска и проверки соответствующего закреплённого
движка; ошибки сводятся к allow-listed кодам.

Profile handle создаётся службой как случайный непрозрачный идентификатор и
сохраняется GUI в CurrentUser secure storage. Текущая console-session политика
не поддерживает RDP/Fast User Switching; до production потребуется явная
привязка GUI-сеанса к SID владельца.

## Внутренние модули

```text
IPC validator
  -> command serializer / finite-state machine
    -> profile resolver + subscription decision
      -> WireGuard adapter | AmneziaWG adapter | Xray adapter
        -> route manager | DNS manager | WFP manager
          -> reconciliation + state events
```

Адаптеры не вызывают друг друга и реализуются отдельными этапами. Одновременно
активен максимум один управляемый lifecycle. `CONNECTED` выдаётся только после
подтверждения интерфейса, маршрута и обязательной политики, а не после запуска
процесса.

## Права и хранение

- предпочтительно отдельный service SID и минимальные ACL;
- executable/config/state каталоги не доступны на запись обычному пользователю;
- пользовательские секреты остаются в CurrentUser storage, пока службе они не
  нужны; service-секреты — отдельное DPAPI/service-only хранилище;
- временные файлы создаются только в service-owned каталоге и удаляются после
  атомарного применения;
- служба не открывает сетевой порт и не реализует production API клиента.

## Kill switch и восстановление

WFP-фильтры применяются транзакционно до изменения маршрута. Служба хранит
минимальный журнал ожидаемого состояния и при старте сверяет его с ОС. После
crash/reboot она должна либо восстановить полностью подтверждённое подключение,
либо перейти в безопасное отключённое состояние по утверждённой политике, не
оставляя неизвестных маршрутов и фильтров.

## Установка и обновление

Установщик отдельно требует elevation, проверяет подпись всех payload и задаёт
ACL. GUI никогда не запрашивает постоянный запуск от администратора. Обновление
службы требует signed manifest, совместимой версии IPC, health check и
проверенного rollback.
