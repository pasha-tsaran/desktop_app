# Kenai VPN 2.3.1 — Netherlands connection compatibility

The Windows service selects the Firefox REALITY fingerprint for the existing
Netherlands endpoint `147.45.231.194:443`. Already stored activation keys and
opaque profile handles remain valid; no account reset or key reissue is needed.
The Armenian endpoint keeps its existing Chrome fingerprint.

On the tested Windows network, isolated direct Chrome connections sometimes
worked, but parallel requests stalled during TLS negotiation. Firefox passed
40 simultaneous DNS requests plus a subsequent HTTPS exit-country check and
DNS exchange using the same node and credentials. Server TCP counters showed
incomplete TLS exchanges; the precise cause on the network path is not proven.
Increasing the Windows connection-check timeout did not resolve the problem
and was not retained.

The override is deliberately limited to the exact known NL IPv4 address, port,
and existing Chrome profile type in `xray_network_policy.rs`. This is a
compatibility rule for the current two-node deployment, not a general dynamic
server-capability registry. When replacing the NL endpoint, revalidate the
handshake and update/remove this rule explicitly.

Regression tests cover cached NL profile rendering, unchanged Armenian behavior,
and endpoint scoping. Normal Xray logging remains disabled and the bounded
data-plane check remains required before reporting Connected.

The installer was prepared for manual installation. A live full-TUN test of
this final build was not performed because the operator requested that the
currently connected VPN must not be interrupted. Standalone transport probes
do not replace that final Windows acceptance test.
